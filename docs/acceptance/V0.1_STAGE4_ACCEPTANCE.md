# V0.1 Stage 4 验收记录

## 本轮范围

Stage 4 消费 Stage 3C 的 `reviewed_materials.json` 和 Agent 生成的 `classification-plan.json`，过滤真实有效 collected Materials，复制图片到独立报告 `assets/`，生成 `classification.json`、`report_data.json` 和 HTML 图墙。分类器与报告不重新执行采集、语义审核或机械校验，不进入 Stage 5。

## Classification Plan Contract

计划必须提供非空 `classification_dimension`、`classification_reason`、唯一分组名称、非空分组原因和 `material_ids`。每个有效 collected Material 必须且只能出现在一个分组；不得引用 rejected/pending/unavailable 或未知 ID。`material_labels` 的 labels 为字符串键值，并原样保留。Python 不根据产品类型、notes 或关键词推断分类。

## 报告与状态边界

主图墙只展示同时满足 semantic accepted、quality accepted、collection collected 且路径有效的素材。Stage 4 将图片复制到自身 `assets/`，因此移动整个输出目录后报告仍可用。无有效素材时输出 `unavailable`，不生成空图墙，并展示 fallback 中的 open 项；resolved 项不作为缺失项展示。报告自身再次执行 collected-only 防御性过滤。

## 独立复验补正

- Stage 4 不再将 Material ID 直接拼入资产目标路径。资产文件名使用 Material ID 的 SHA-256 前 16 位十六进制摘要和已审核图片后缀，稳定写入 `output/assets/`；写入前再次通过 `target.resolve().relative_to(assets_dir.resolve())` 防御性确认目标未逃逸。原 Material ID 继续原样保留在 JSON。
- Stage 1、Stage 2 与 legacy 非 Stage 4 分支不再调用需要 Agent Classification Plan 的严格分类器，而是明确输出“正式动态分类仅在 Stage 4 Agent Classification Plan 流程执行”的 `unavailable` 占位。正式结构化 task、`--materials-file`、真实可解码图片与 `semantic_status=accepted` 的 Stage 2 CLI 回归已验证 collected Material 和 `materials.json` 正常生成，且不要求 `--classification-plan-file`。
- Stage 4 会按 task 中每个 `product_name + target_page` 检查 fallback 状态与 collected 事实：存在 collected 时 fallback 可缺失或必须为 `resolved`；没有 collected 时已有 fallback 不得为 `resolved`。矛盾状态直接拒绝，不推断原因文本。
- 报告自包含验证会在生成后真实移动整个输出目录并确认原目录失效，再从新目录启动本地 HTTP Server。真实 Chromium 已验证主图 `.asset-image` 成功加载且 `naturalWidth > 0`，点击放大成功，dialog 图片同样 `naturalWidth > 0`。
