# 竞品分析 Skill V0.1 执行架构

更新时间：2026-09-01

## 1. 架构目标

将已确认的 V0.1 产品定义落成一条可实现、可验证、可扩展的执行链路：

> 用户一句自然语言需求 → 理解目标 → 确定竞品范围 → 采集页面 → 统一素材 → 动态分类 → 生成可直接浏览并放大截图的 HTML 网页报告。

V0.1 优先验证“搜集 + 筛选 + 分类 + 浏览”是否真实可用，不追求一次实现所有采集方式和复杂分析能力。

## 2. 总体执行架构

V0.1 分为五层：

1. 需求理解层
2. 竞品规划层
3. 页面采集层
4. 素材标准化层
5. 动态分类与网页报告层

核心执行顺序：

```text
用户自然语言需求
        ↓
需求解析
        ↓
生成并筛选竞品清单
        ↓
逐个寻找目标页面
        ↓
公开来源采集
        ↓
页面筛选与质量判断
        ↓
统一进入竞品素材池
        ↓
基于实际素材动态分类
        ↓
生成 HTML 网页报告
        ↓
直接浏览 / 点击截图放大
```

如果关键竞品无法从公开来源获得可靠页面，则记录缺失状态，再进入用户上传截图或 iPhone 镜像人工补充流程。

## 3. 需求理解层

### 3.1 输入原则

用户只需要通过自然语言描述调研需求，不要求填写固定表单。

例如：

- “帮我搜集一下海内外热门产品的搜索结果页。”
- “看看不同产品的用户个人主页怎么做。”

只要需求已经足够明确，Skill 应直接执行，不为了形式完整而连续追问用户。

只有当目标页面或调研对象无法可靠判断时，才需要补充询问。

### 3.2 内部任务结构

需求解析后转换为统一的结构化任务对象，建议至少包含：

```json
{
  "request": "帮我搜集一下海内外热门产品的搜索结果页",
  "research_goal": "为产品设计提供页面参考",
  "target_page": "搜索结果页",
  "regions": ["CN", "Global"],
  "product_scope": [],
  "specified_products": [],
  "platforms": [],
  "constraints": [],
  "collection_status": "planned"
}
```

字段允许根据真实实现调整，但应保持结构简洁，避免为了未来可能使用的能力过度设计。

## 4. 竞品规划层

### 4.1 竞品范围生成策略

根据用户输入分三种情况：

1. 用户已指定竞品：优先按照用户指定范围执行，必要时仅补充少量具有明显参考价值的对象。
2. 用户指定了范围但未指定具体产品：Skill 根据地区、产品类型和代表性生成候选池，再筛选本次清单。
3. 用户未指定产品范围：Skill 根据目标页面生成具有代表性的竞品候选池，并从中筛选本次调研对象。

### 4.2 入选原则

竞品选择优先考虑：

- 与目标页面直接相关。
- 在对应市场或产品类型中具有代表性。
- 对当前设计问题具有参考价值。
- 页面存在可获取的可靠素材。
- 在同一报告中形成有意义的横向差异。

竞品数量不追求越多越好。目标是获得“足够有代表性”的样本，而不是穷举全部产品。

### 4.3 竞品清单结构

每个候选竞品至少记录：

```json
{
  "product_name": "小红书",
  "region": "CN",
  "product_type": "内容社区",
  "reason": "内容搜索与社区结果组织具有代表性",
  "priority": "high",
  "collection_status": "pending"
}
```

入选理由保持简短，主要用于解释为什么该产品值得采集，不在此阶段展开长篇分析。

## 5. 页面采集层

### 5.1 采集优先级

V0.1 采用固定优先级：

1. 专业 UI / 设计参考数据库。
2. 公开 Web 来源。
3. 用户上传截图。
4. iPhone 镜像真机截图。

优先自动化、公开、稳定、页面质量较高的来源；真机采集只作为关键竞品公开素材不足时的补充方式。

### 5.2 一级来源：专业 UI 数据库

优先尝试：

- https://uinotes.com/
- https://refero.design/apps/search
- 后续确认有效的其他 UI 数据库。

优先原因：页面通常更完整、干净，更适合作为设计参考。

### 5.3 二级来源：公开 Web

当 UI 数据库无法提供可靠页面时，可继续查找：

- 产品官网。
- 官方帮助中心。
- 官方设计或产品案例。
- 可信的公开设计案例。
- 其他能够明确确认产品、页面和版本上下文的公开来源。

### 5.4 页面质量筛选

进入素材池前至少检查：

- 是否真的是用户要求的目标页面。
- 产品身份是否可靠。
- 页面是否足够完整、清晰。
- 是否存在严重裁切或大量无关网页 UI。
- 是否明显过时。
- 是否只是营销海报、概念图或无法确认真实性的展示图。

不为了凑数量保存低质量或明显不匹配的页面。

### 5.5 采集失败处理

如果某个重要竞品无法找到可靠公开素材：

- 记录失败原因。
- 标记为 `needs_manual_capture` 或等价状态。
- 不使用低质量截图替代。
- 在公开来源阶段结束后统一处理人工补充项。

## 6. 用户上传与 iPhone 镜像补充

### 6.1 用户上传截图

用户上传截图应与在线采集结果进入同一个素材标准化流程，不建立第二套报告结构。

需要补充或推断的元数据包括：

- 产品名称。
- 页面名称。
- 平台。
- 来源类型。
- 必要说明。

无法可靠判断的信息应保持未知，不编造版本、时间或页面状态。

### 6.2 iPhone 镜像

V0.1 不把 iPhone 镜像自动化作为 MVP 核心实现。

触发条件：

- 该产品属于本次调研的关键竞品。
- 公开来源无法获得可靠目标页面。
- 用户愿意授权并配合进入对应 App 页面。

执行方式：

1. Skill 明确说明缺失的是哪个竞品、哪个页面。
2. 用户通过 iPhone 镜像打开对应 App 和目标页面。
3. 在用户授权和配合下完成截图。
4. 截图进入统一素材池。

如果用户不方便真机补充，则保留缺失状态，不阻塞其他竞品报告生成。

## 7. 素材标准化层

### 7.1 统一素材池原则

所有来源最终必须转换为统一的竞品素材结构。

报告生成、动态分类和后续分析只读取统一素材池，不直接依赖具体采集来源。

这意味着：

> UI Notes、Refero、普通 Web、用户上传和真机截图，在进入报告前都必须标准化。

### 7.2 页面素材数据结构

V0.1 建议至少包含：

```json
{
  "id": "xiaohongshu-search-01",
  "product_name": "小红书",
  "page_name": "搜索结果页",
  "region": "CN",
  "product_type": "内容社区",
  "platform": "iOS",
  "image_path": "assets/xiaohongshu-search-01.png",
  "source_type": "ui_database",
  "source_url": "",
  "captured_at": "",
  "notes": "",
  "quality_status": "accepted",
  "collection_status": "collected"
}
```

### 7.3 字段原则

- `image_path` 必须指向最终报告可以正常引用的本地或构建产物素材。
- `source_type` 用于区分 UI 数据库、Web、用户上传、真机等来源。
- `source_url` 在公开来源可用时保留，用于追溯，不作为最终查看截图的唯一方式。
- `captured_at` 无法可靠确认时允许为空，不编造。
- 可根据实现增加页面状态、登录状态、版本、设备等字段，但不是 V0.1 MVP 必填项。

## 8. 动态分类层

### 8.1 先采集，再分类

V0.1 不在采集前固定唯一分类方式。

执行顺序必须是：

> 完成主要素材采集 → 观察实际差异 → 判断最有价值的分类方式 → 组织报告。

例如“搜索结果页”最终可能更适合按：

- 国内 / 海外。
- 内容社区 / 短视频 / 电商 / AI。
- 综合结果型 / 分栏结果型 / 内容流型 / AI 回答型。

具体采用哪一种，应以帮助设计师快速理解差异为标准。

### 8.2 分类输出结构

建议形成：

```json
{
  "classification_dimension": "页面结构模式",
  "groups": [
    {
      "name": "内容流型",
      "reason": "结果以连续内容流为主要组织方式",
      "asset_ids": ["product-a-01", "product-b-01"]
    }
  ]
}
```

分类说明保持简短，不在这一阶段扩展为长篇分析。

## 9. HTML 网页报告层

### 9.1 V0.1 页面结构

网页保持简单，截图浏览优先。

建议结构：

1. 调研目标。
2. 本次竞品范围与样本数量。
3. 分类说明。
4. 按分类展示的竞品卡片墙。

每张竞品卡片至少包含：

- 产品名称。
- 页面截图。
- 页面类型 / 当前分类。
- 一句必要说明。

### 9.2 图片查看要求

- 截图必须直接显示在 HTML 内。
- 点击截图后通过 Lightbox、Modal 或等价方式放大。
- 放大后应能查看完整页面细节。
- 不允许报告主体只提供图片 URL 或外部页面链接。

### 9.3 V0.1 暂不实现

- 复杂 Dashboard。
- 雷达图或打分系统。
- 大量动画效果。
- 长篇 AI 竞品优劣分析。
- 商业模式或战略分析。

## 10. 模块解耦原则

V0.1 不允许“边搜索边直接拼最终报告”。

主链路应拆为清晰阶段：

```text
需求解析
→ 竞品规划
→ 页面采集
→ 页面筛选
→ 素材标准化
→ 动态分类
→ 报告生成
```

各阶段尽量通过结构化数据传递。

这样后续新增新的采集来源时，只需要将素材转换为统一结构，不应大范围修改分类和报告模块。

## 11. V0.1 MVP 实现范围

第一阶段 Codex 实现只要求跑通：

```text
自然语言需求
→ 需求解析
→ 生成竞品清单
→ 公开来源采集
→ 页面筛选
→ 统一素材 JSON
→ 动态分类
→ HTML 报告
```

MVP 暂不要求：

- iPhone 镜像自动化。
- 完整用户上传工作流自动化。
- 所有竞品都必须采集成功。
- 复杂分析与高级网页视觉效果。

关键竞品公开素材缺失时，应能够清晰记录并继续完成其余报告。

## 12. 第一轮真实任务

第一轮建议使用以下任务验证完整链路：

> 帮我搜集一下海内外热门产品的搜索结果页。

重点验收：

1. 竞品范围是否具有代表性。
2. 搜集到的图片是否确实是目标页面。
3. 页面质量是否足够用于设计参考。
4. 分类是否帮助横向理解不同模式。
5. HTML 是否可直接浏览，并可点击放大截图。

第一轮不以分析文字丰富程度作为主要验收标准。

## 13. 实现优先级

建议 Codex 按以下顺序实现：

1. 定义统一素材数据结构。
2. 定义 Skill 主执行流程和阶段输入输出。
3. 实现公开来源采集。
4. 实现页面质量筛选与失败记录。
5. 实现动态分类。
6. 实现 HTML 报告与图片放大。
7. 接入用户上传截图。
8. 最后补充 iPhone 镜像人工 fallback 流程。

## 14. 架构成功标准

V0.1 架构达到可实现状态，需要满足：

- 每一阶段职责清楚。
- 数据可以在阶段之间结构化传递。
- 所有页面素材进入统一素材池。
- 采集失败不会导致整个任务失败。
- 可以后续增加新来源而不重写报告模块。
- 第一阶段可以用一个真实任务完整跑通公开来源到 HTML 报告的链路。
